## 本次最重要的结论

1. 知识库值得被裁剪为长期开发参考；是否值得收录与是否立刻实施是两个决定。项目一度只按眼前问题筛选知识，经用户纠正才补成按问题查阅的参考文档。
2. 补齐真实读取入口和计划交接，可以得到可独立确认的工程收益，但未使真实Main稳定生成可直接采用的工期计划。负结果保留，未扩大整案或增加固定审查链。
3. 知识库对历史“2/46”计数的质疑促成一次新的离线审计，补强了目标集合与指定字段变化的证据；仍不是新整案成功或外部独立复现。
4. 指导较适合帮助发现责任层与约束误用，目前不足以提供“复杂语义问题按此改就能解决”的通用配方。不能因这一局限否定其参考价值，也不能因道理合理就宣称业务收益。

## 真实Main验证：有工程收益，尚无完整业务通过

只涉及一个真实历史工程文稿任务。完整源资料与899个有效正文位置复制到隔离测试环境。旧版与候选使用同一正式Main工厂、业务模型配置、Skill和实际读取工具；没有人工整理的数量、来源分类或正确排期输入。

验证限制为关联工序规划子流程：只读业务资料，允许保存私有共同计划，保存后停止。没有真实正文编辑、完整HTTP客户端或最终保存验收。预登记范围回执未完整进入模型历史，带来重复登记恢复；这属于装置限制，影响耗时比较，不能记为生产事故。

合计1个任务、3次规划子流程、29次模型请求，估价0.494606元。业务模型为官方deepseek-flash滚动别名，high、输出上限16384；别名不是固定模型快照。按当时留档输入/缓存/输出1/0.02/4元每百万token估算，非账单或本报告重新核验的官网价格。输入累计按每次请求求和，缓存分别计费。没有Java编辑成本，因为没有调用；开发助手、阅读、开发和人工审查成本未知，不能写总投入仅0.49元。

候选确实自主使用局部导航并保存依据，23项聚焦程序检查覆盖详细材料读取、跨任务拒绝、旧计划兼容及依据进入实际编辑合同。调用较少只支持当次观测，不能宣称同质量降本；三份计划均未通过，没有可计算的每成功任务成本。

已观察的残余包括：未核清来源就将旧正文时序列为受保护条件；共同表改了前置工序日期，但具体章节改法漏同步相应旧表行。后者的原行已经完整返回给Main，不能继续归为读取截断。编辑器也会收到共同表，仍可能补正，故不能在尚未编辑时断言最终保存必错。

局部计算原型曾在人工绑定关系与同一草案下达到普通1/3、计算反馈3/3的数字检查结果；它不是本次自主Main对照，也没有解决要求来源和对象绑定。不能把两个层次拼成“程序计算已解决完整工期”。

## 历史2/46审计的更正

知识库v0.19发现旧离线脚本结果字段含固定计数，相关断言没有独立证明完整集合。本项目确认该质疑成立，保留原脚本和原结果，并新增零模型、零写入回放审计。

| 新审计项 | 结果 |
| --- | ---: |
| 原唯一修复目标 | 48 |
| 展开后唯一目标 | 48 |
| 请求修正目标 | 2 |
| 实际expectedChange变化目标 | 2 |
| 该字段保持不变目标 | 46 |
| 目标集合完全一致且无重复 | 是 |

核查方式是对原目标和展开后的目标建立身份映射，比较集合、重复及每个目标的expectedChange差异，再与请求中的修订目标核对。结果由源记录计算，不再输出固定通过数字。

这补强“原调用离线回放”的集合与该字段证据；不能证明其他字段均不变、语义正确、模型自主纠错或一次真实整案成功。原始客户记录未公开，外部维护者仍不能独立复现；报告身份为项目方新增审计，不是本库自身验证。之前整案失败记录继续有效。

## 值得补入知识库的经验

### 1. 分开知识收录、采用与效果声明

建议落点：trial入口或08的采用说明，不必新增第13条核心。

> 评估知识用于长期参考时，分别判断适用范围、依据强度与立即实施价值。当前不实施的方法仍可按触发条件保留；收录不代表强制执行或已验证收益。必要边界由合同和事实支撑，经验默认允许例外，具体效果承诺由对应任务证据支撑。

这能避免两个极端：把所有知识变成当前待办，或因没有眼前落地机会而排除有用参考。项目本轮已按此接入，但尚未计量后续查阅和开发收益。该问题发生在本项目的评估习惯，不应归咎于本库原文要求。

### 2. 信息“性质”和信息“保真”分别核对

建议落点：02，补一例即可。

数据库中的“详细材料”“原文”字段可能经过LLM提取；字段名不证明逐字保真。原附件、提取、摘要、生成计划和已保存正文分别有用途。发现提取结果冲突时，先把冲突限定在已看到的表示；未回到附件，不能宣称原附件自身矛盾。

本项目实际经历：旧工具未暴露详细提取，属于明确工程缺口；暴露后Main仍未充分核关键条件，属于另一层问题。可用“存在→可访问→返回→入模→采用→下游消费”定位缺口，但不能把每个任务强制变成六份回执。

### 3. 共同结论和具体动作的重复表达值得单独诊断

建议落点：02的跨段关系，或06负例。共同计划、保护列表、逐节改法反复表达相同日期和条件，可能生成互相矛盾的版本。可考虑一份有效安排配合明确位置引用，或对已声明关系给出窄计算反馈。

**这是候选，不是已证修法。** 程序核引用和数值不能替代业务对象识别；删掉逐节细节也可能把负担转给下游。验证应分别看计划、动作与真实保存，不能只看少写了几遍数字。现有消费者若已足够，不应另建结构化平台。

### 4. 不同层次的失败不能把彼此的收益抹掉或放大

建议沿04已有证据分层补例：工具可达性修复可以保留，即便完整业务未过；完整计划未过也不等于工具无收益。反过来，工程测试、模型自主采用和业务完成不能互相替代。

本项目有正结果（确定机制修复）、持平（七份历史续聊首请求大小）、负结果（自主Main计划未达标）、费用增加（既有审查形成结论但耗时/成本上升）。它们都应保留，不能挑一种指标宣布整库或整版胜出。

### 5. 发布判断要核实候选和配置，不用开发分支名代替

这是项目长期开发经验，适合补到08交付视角。发布时源码默认、环境变量、模型注册表、共享业务更新和持久状态共同决定行为。只更新源码，旧环境变量仍可能覆盖验收过的模型名；开发分支也可能缺少主干已合并的其他业务修复。

本轮上线准备只读核对发现了上述具体差异，尚未部署，不能称为已避免线上事故或已获得发布收益。方法是核现有发布信息、明确最终候选与少量受影响路径，不要求通用部署平台或额外哈希体系。

## 我们怎样接入，怎样避免过重

项目保留自身AGENTS、产品原则和业务标准；AGENTS按问题指向本地裁剪的开发参考，参考独立可读，外部库作为研究与更新来源。目标业务Agent不常驻加载整库，外部目录也不是启动依赖。

长期参考覆盖目标/判断标准、责任层、信息表示、模型可靠性、修订恢复、共同方案、评测成本和执行边界。上游更新按差异审阅；模型特定技巧和效果更需复核，而不虚报完成等稳定边界不因来源超过固定月数失效。

新增负担包括维护一份按主题参考及来源版本评估，实际阅读和人工工时未知。接入只完成文档、路由和内容一致性检查，尚未证明未来开发更快。没有新增固定审查Agent、多模型路由、通用依赖图或新的生产状态owner。

建议维护者优先保留核心12条，用少量负例和采用说明补足上述边界；不将本项目固定预算、次数、字段或业务规则升级为所有项目默认。下一轮独立项目反馈应观察：是否更快选到正确责任层、是否减少无效迭代、是否反而增加无价值阅读/审查。未发生改变时如实记为已有实践或冗余参考。
