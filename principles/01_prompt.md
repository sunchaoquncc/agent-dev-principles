# 从任务要求写出可测提示

适用D01/D03/D10。本文件教开发助手构建目标 Agent 的提示；开发原则、研究依据和测试报告不应一起塞进目标系统提示。

## 构建顺序

1. 先看任务输入和期望输出，找出需要模型做的判断，以及最容易混淆的边界。没有样例时先提出少量设计样例并标注假设。
2. 写出任务目标、材料含义、必须保留的内容、允许改变的内容及输出用途。格式仅在读者或下游程序确实需要时约束。
3. 对真实存在的决策分歧写条件与动作：何时取资料、何时可回答、何时缺信息、何时停止。不要把所有异常穷举成每轮长指令。
4. 将稳定行为放默认指令，任务参数放当次输入，可变事实放知识/工具，确定性校验放代码；只有执行到相关阶段才加载专项方法。
5. 模型持续误解某个边界时，补有区分力的输入/输出例。示例应说明区别，不代替政策；不要默认大量few-shot或要求展示完整思维过程。
6. 在相同模型、工具和输入条件下，对照代表性与失败样例。看错误是否减少、是否产生新的退化，再决定保留或撤销修改。

## 一份可起步的任务规格

- 任务与成功结果：模型究竟生成、判断或提取什么？
- 输入解释：哪些是指令、事实、候选内容、历史状态？
- 决策边界：允许推断到哪里？缺什么信息会影响继续？
- 输出契约：给人读还是给程序处理？哪些要求可被检查？
- 必要示例：什么情况容易误判，期望差异是什么？

这不是要求所有提示包含五个标题；没有作用的项不加入运行上下文。短提示不天然好，长提示不天然坏。

## 从空泛要求到可观察行为

| 空泛写法 | 可测试的改写方向（设计例，不是通用系统提示） |
|---|---|
| 认真准确地整理资料 | 区分材料明示与自己的推断；结论附可回查位置；材料冲突时保留差异 |
| 把文章改得更好 | 明确要改变的风格和结构，以及不得改变的人物、数字、立场；按需求检查遗漏 |
| 节省上下文 | 工具默认返回当前判断所需字段与继续读取入口；预算与截断由编排实现 |
| 有问题就多想几遍 | 指出可验证的缺陷并修复；只有发现具体问题才重试，设置退出条件 |

## 失败应修哪里

模型拿到正确事实却持续误解任务：检查提示、样例或模型能力。事实缺失/污染：先修输入。工具返回过大/歧义：先修契约。计算或权限出错：修代码。反复无效循环：修编排。提示可以提出假设，但不能把所有问题都掩盖成指令不够长。

主观质量由使用者、编辑或业务专家提供标准，可做盲评比较；不要让同一个生成模型的自评分成为唯一依据。模型换代后重新检查提示效果，不把旧代技巧当固定标准。
